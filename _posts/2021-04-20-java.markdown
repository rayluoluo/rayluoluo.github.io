## AOT 
- JDK 9 引入了一种新的编译模式 `AOT(Ahead of Time Compilation)` 。和 JIT 不同的是，这种编译模式会在程序被**执行前**就将其编译成机器码，属于静态编译（C、 C++，Rust，Go 等语言就是静态编译）。AOT 避免了 JIT 预热等各方面的开销，可以提高 Java 程序的启动速度，避免预热时间长。并且，AOT 还能减少内存占用和增强 Java 程序的安全性（AOT 编译后的代码不容易被反编译和修改），特别适合云原生场景。
- AOT 编译无法支持 Java 的一些动态特性，如反射、动态代理、动态加载、JNI（Java Native Interface）等。然而，很多框架和库（如 Spring、CGLIB）都用到了这些特性

1. -Xms

   管控：Java 堆（Young+Old）初始分配大小
   启动 JVM 时，操作系统直接给进程分配对应内存；
   示例：-Xms256M → 程序刚启动堆就占用 256M；
   若 -Xms = -Xmx，堆固定不变，不会动态扩容 / 缩容（你日志就是这种配置）。

2. -Xmx

   管控：Java 堆（Young+Old）最大容量上限
   Young 区 + Old 区 总和不能超过该值；
   示例：-Xmx256M，整个堆最多只能使用 256MB；
   堆占用触达上限，无法分配新对象，触发 GC；GC 回收不出内存则 OOM。

3. -Xmn

   管控：新生代 Young 总容量上限（Eden + S0 + S1）
   仅限制新生代，不影响老年代；
   老年代可用空间 = -Xmx 总堆大小 − -Xmn；
   G1 收集器不推荐手动指定-Xmn，G1 会自动动态调整新生代大小；Parallel/CMS/Serial GC 常用。
   配套比例参数：-XX:SurvivorRatio=8 控制 Eden 和 Survivor 比例。

4. -XX:MaxDirectMemorySize

   Direct Memory 直接内存。管控：堆外直接内存最大值
   不属于 Java 堆，不占用 -Xmx 空间；
   NIO、Netty、文件 IO 大量使用allocateDirect时消耗；
   不手动配置默认等于 -Xmx；
   超出限制抛出 `java.lang.OutOfMemoryError: Direct buffer memory`。

5. -Xss：

    线程栈内存，每个线程独立，不属于堆、不属于直接内存；

6. -XX:MaxMetaspaceSize

    元空间上限，存放 Class 字节码，和堆隔离；

8. -XX:G1HeapRegionSize

    G1 堆分区大小，只是划分堆的粒度，不改变堆总容量。

举例：
```java
JVM参数：-Xms1G -Xmx2G -Xmn300M -XX:MaxDirectMemorySize=512M
```

- Java 堆初始 1G，最大 2G；
- 新生代固定 300M（Eden+S0+S1），老年代最大 = 2G-300M=1700M；
- NIO 直接堆外内存最多使用 512M，独立于堆之外。

## 直接内存等价于堆外内存？

**不等价，是包含关系**，堆外内存是大集合，直接内存只是堆外内存的其中一种。

1. 定义区分

   **堆外内存（Native Memory）**

   JVM 进程中，不在 Java 堆（-Xmx/-Xms）里、直接向操作系统 malloc/mmap 申请的内存，统称堆外内存。

   包含所有下面这些区域：
    - NIO DirectBuffer 分配的直接内存
    - Metaspace / PermGen（方法区）
    - CodeCache（JIT 机器码缓存）
    - 线程栈：虚拟机栈、本地方法栈（-Xss）
    - JNI 原生代码申请的内存
    - JVM 内部缓冲区、符号表、管理内存
    - Panama FFI 原生内存分配

   **直接内存（Direct Memory）**

   特指 ByteBuffer.allocateDirect() 分配的 IO 缓冲区，只是堆外内存的子集，唯一受 -XX:MaxDirectMemorySize 限制。

2. 核心差异点

   | 维度 | 堆外内存 | 直接内存 |
       | --- | --- | --- |
   | 范围 | 所有非 Java 堆内存，范围极大 | 仅 NIO DirectBuffer 缓冲区 |
   | 管控参数 | 分多块独立参数：-Xss、MaxMetaspaceSize、ReservedCodeCacheSize 等 | 单一参数 -XX:MaxDirectMemorySize |
   | 回收机制 | 各区域释放逻辑不同：栈随线程销毁、CodeCache 按需清理、元空间靠类卸载 GC | 依赖堆内 DirectByteBuffer 对象 GC，通过 Cleaner 释放 |
   | OOM 异常 |	分多种：StackOverflow、Metaspace OOM、CodeCache 满	| java.lang.OutOfMemoryError: Direct buffer memory


## GC

一个可以触发JVM GC的Java程序
```java
package com.github.rayluoluo.snippet.jvm;

import java.util.ArrayList;
import java.util.List;

/**
 * JDK21 JVM GC演示程序
 * VM启动参数建议（JDK21 ZGC）：
 * -Xms256m -Xmx256m -XX:+UseZGC -Xlog:gc*:file=./logs/gc.zgc.log,stdout:time,uptime,level,tags:filesize=10M,filecount=5 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./dump/ -XX:OnOutOfMemoryError="taskkill /F /PID %p"
 * 传统G1测试参数：-XX:+UseG1GC
 * -Xms256m -Xmx256m -XX:+UseG1GC -Xlog:gc*:file=./logs/gc.g1gc.log:time,uptime,level,tags:filesize=10M,filecount=5 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./dump/ -XX:OnOutOfMemoryError="taskkill /F /PID %p"
 */
public class JvmGCDemo {
    // 大对象数组，占用堆内存
    static class BigObject {
        private byte[] data;
        public BigObject(int size) {
            data = new byte[size];
        }
    }

    // 全局集合：内存泄漏核心（强引用无法被GC回收）
    private static final List<BigObject> leakList = new ArrayList<>();

    public static void main(String[] args) throws InterruptedException {
        System.out.println("==== JDK21 JVM GC 演示开始 ====");
        // 1. 频繁创建短命对象 -> 触发Minor GC（新生代回收）
        createShortLiveObj();
        System.gc(); // 建议Full GC，不保证立即执行
        Thread.sleep(2000);

        // 2. 创建大量长期存活对象，晋升老年代
        createLongLiveObj();
        Thread.sleep(3000);

        // 3. 模拟内存泄漏：全局集合持有对象，无法回收，最终OOM
        try {
            createLeakObject();
        } catch (OutOfMemoryError e) {
            System.err.println("发生OOM内存溢出！");
            e.printStackTrace();
            // 发生OOM自动dump堆快照，配合JVM参数 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=dump.hprof
        }
    }

    /** 短命对象：栈上分配/新生代快速回收 */
    private static void createShortLiveObj() {
        for (int i = 0; i < 1000000; i++) {
            BigObject obj = new BigObject(1024); // 1KB小对象
        }
        System.out.println("短命对象创建完成，大概率触发Minor GC");
    }

    /** 长期存活对象：多次GC存活后晋升到老年代 */
    private static void createLongLiveObj() throws InterruptedException {
        List<BigObject> temp = new ArrayList<>();
        for (int i = 0; i < 50000; i++) {
            temp.add(new BigObject(1024 * 10)); // 10KB
        }
        System.gc();
        Thread.sleep(1000);
        System.out.println("长期对象完成，部分对象晋升老年代");
    }

    /** 内存泄漏：静态集合强引用，对象永远无法释放 */
    private static void createLeakObject() {
        while (true) {
            leakList.add(new BigObject(1024 * 1024)); // 1MB对象持续放入静态集合
        }
    }
}
```

  - JVM 即将抛出 OOM，堆完全耗尽前，ZGC 强制发起最后一轮抢救式 GC，执行一次特殊的全量回收（Warmup GC），尝试： 
    - 强制清理所有软引用、弱引用 
    - 全堆完整标记 + 重定位，尽力释放任何可回收内存
  - OOM 后 JVM 尝试最后一次 GC 抢救，已无意义

### MMU (Minimum Mutator Utilization)

- Mutator = 应用业务线程（执行你的 Java 代码、创建对象、处理请求）
- MMU：最小应用线程利用率，衡量一段时间内业务线程能真正运行的时间占比，用来量化 GC 对业务的干扰程度。

$$
MMU = \frac{\text{业务线程运行时间}}{\text{业务线程运行时间} + \text{GC线程停顿或阻塞时间}}
$$

日志样例：
```text
MMU: 2ms/98.8%, 5ms/99.4%, 10ms/99.7%, 20ms/99.8%, 50ms/99.9%, 100ms/100.0%
```

- Xms：滑动观测窗口（2ms、5ms、10ms、20ms、50ms、100ms）
- Y%：在这个窗口内，应用线程可用时间占比
- GC0 MMU 2ms/98.8%：健康，极短窗口内业务可用率极高； 
- GC1 MMU 2ms/98.3%：轻微变差，因为出现了 33ms Allocation Stall，挤占业务时间。

MMU 统计包含两类阻塞：
- GC Pause（Mark Start/End、Relocate Start 微秒 STW）
- Allocation Stall 分配阻塞（线程等待 GC 完整一轮，严重拉低 MMU）

日志里 MMU 小幅下降，根源就是 Allocation Stall。

  - Young GC 停顿飙升至 24ms，响应延迟恶化。

- GC4~GC9：持续 Evacuation Failure，老年代持续填满
  - 每一次 Young GC 都转移失败，老年代 region 一路涨到 254 个（占用 254M）

- GC10 起：疯狂 Full GC 压缩
  - 并发标记循环Concurrent Mark Cycle频繁启动又中途 Abort（GC10、GC15），标记被 Full GC 打断，并发回收完全失效

## 工具

### jmap
jmap 是一个用于生成 Java 堆转储文件的工具，可以帮助你分析 JVM 的内存使用情况。

可用于手动导出dump文件，使用MAT分析内存使用情况：

```shell
jmap -dump:format=b,file=dump.hprof 1234
```

增加如下jvm启动参数，OOM 自动生成dump文件：

```java
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./dump/
```

### MAT
MAT (Memory Analyzer Tool) 是一个用于分析 Java 堆转储文件的工具，可以帮助你找到内存泄漏的原因。

#### 前置准备

1. 获取堆 dump 文件
   - OOM 自动 dump：启动参数添加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/xxx/heap.hprof`
   - 手动导出：`jmap -dump:format=b,file=heap.hprof` 进程PID

2. 适配 MAT 内存：修改`MemoryAnalyzer.ini`，根据 dump 大小设置-Xmx（dump 为 200MB 则设-Xmx1024m，大文件成倍放大）

3. 启动 MAT，File -> Open Heap Dump 加载.hprof文件

#### 步骤 1：优先执行泄漏嫌疑报告（Leak Suspects Report）

1. 打开 dump 后弹窗选择 Leak Suspects Report，点击 Finish 自动分析；

2. 报告核心阅读点：
   - 饼图：占堆内存最高的对象 / 类；
   - Suspect 1：MAT 自动标记的泄漏嫌疑人，包含占用内存大小、引用链、可疑代码类；

3. Demo 场景：报告会直接标记JvmGCDemo$BigObject为泄漏源头，给出总占用内存。
25127对象占用空间`258,749,256 ÷ 1024 ÷ 1024 = 247.02MB`

    ![导入 dump 文件到 MAT](/assets/jvm/mat.png)

    ![内存泄漏嫌疑报告](/assets/jvm/leak_suspects_report.png)

#### 步骤 2：查看 Histogram 直方图，定位占用最高的业务类

点击Histogram工具，在顶部正则输入框过滤业务类（如JvmGCDemo\$BigObject）；

或点击Retained Heap降序排序，查看类总实例数、总占用堆内存；

**关键指标：**

1. Objects：该类实例总数量（Demo案例 25127 个）；

2. Retained Heap（保留堆）：该类所有对象连带子对象合计占用内存（判断泄漏核心指标）；如果当前对象被 GC 回收，能连带一起释放的全部堆内存总和。包含三部分：
   - 对象自身的 Shallow 内存；
   - 该对象直接引用的所有子对象；
   - 子对象再递归引用的所有下级对象。

3. 区分：Shallow Heap（浅堆） 仅对象自身在堆中占用的内存大小，不包含该对象引用的其他任何子对象。组成（64 位 JVM + 压缩指针开启，主流生产环境）
   - 对象头：12 字节（Mark Word + 类元指针）
   - 实例字段指针：每个引用类型占 4 字节
   - 对齐填充：保证内存 8 字节对齐（不足则补零）。 

4. 排查泄漏**只看 Retained Heap**。

    ![直方图](/assets/jvm/histogram.png)

#### 步骤 3：追溯 GC 根引用链（找到对象无法回收的根源，核心步骤）

1. 方式 A（最简，推荐）：Merge Shortest Paths to GC Roots

    选中 BigObject 实例；右键 List objects -> Merge Shortest Paths to GC Roots；展开链条，确认是谁持有该对象。

    ![追溯 GC 根引用链](/assets/jvm/gc_root.png)

2. 方式 B：with incoming references 单对象溯源

    选中单个 BigObject 实例；右键 List objects -> with incoming references；展开链条，确认是谁持有该对象，和上面 GC 根链路结果一致。

    ![单对象溯源](/assets/jvm/incoming_reference.png)

#### 步骤 4：分析对象内部，验证内存占用细节（区分真实大对象 / 空壳）

1. 选中可疑对象（BigObject）；右键 List objects -> with outgoing references；查看对象自身持有的所有子属性（Demo场景看data字节数组，数组元素是10KB对象）；

    ![分析对象内部](/assets/jvm/outgoing_references.png)

2. 也可以通过OQL查询分析：

#### 步骤 5：Dominator Tree 支配树，定位内存大户

1. 点击 Dominator Tree 图标工具，按Retained Heap降序，能直接看到 “支配对象”：释放该对象即可释放大量堆内存；
