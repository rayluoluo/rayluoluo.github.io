## 安装 WSL

管理员 PowerShell，正确开启 WSL

```shell
wsl --install
```

执行完成后重启电脑。

重启之后验证：

```shell
wsl --list --verbose
```
查询结果只要有默认 Ubuntu 发行版，WSL2 环境就绪：

```shell
  NAME              STATE           VERSION
* Ubuntu-24.04      Running         2
```

##### 编写 Kafka 配置 kafka-values.yaml

```yaml
# kafka-values.yaml
## 镜像配置
image:
  repository: bitnami/kafka
  tag: 3.9.0-debian-12-r4
  pullPolicy: IfNotPresent

## 副本数量
replicaCount: 3

## KRaft模式开关（重点！关闭zookeeper）
kraft:
  enabled: true
  # 集群ID，所有节点必须统一，可自定义
  clusterId: "MkYxZjQzNzItODQzMi00YzE4LWI4MDItYjE4MDIwNzI4YjY2"

## 关闭controller分离模式
controller:
  enabled: false

## 启用broker（组合模式下自动包含controller功能）
broker:
  kraft:
    enabled: true
    clusterId: "MkYxZjQzNzItODQzMi00YzE4LWI4MDItYjE4MDIwNzI4YjY2"

## 关闭内置Zookeeper
zookeeper:
  enabled: false

## 存储大小
persistence:
  size: 10Gi

## 资源限制（测试环境可以调低/删除）
resources:
  requests:
    cpu: 200m
    memory: 512Mi
  limits:
    cpu: 1000m
    memory: 1Gi

## 监听地址配置（集群内部通信）
listeners:
  client:
    protocol: PLAINTEXT
  controller:
    protocol: PLAINTEXT

## 内部broker通信协议
interBrokerListenerName: PLAINTEXT

### ===== 可选：自动创建测试topic =====
#provisioning:
#  enabled: true
#  topics:
#    - name: test-topic
#      partitions: 3
#      replicationFactor: 3
```

##### 自定义server.properties配置项

###### 修改yaml文档

```yaml
## 顶层或controller下，增加 extraConfig 或 extraConfigYaml配置

# ========== 全局顶层 extraConfigYaml ==========
extraConfigYaml:
  auto.create.topics.enable: false
  log.retention.hours: 72

# 或

# ========== controller下 extraConfig ==========
controller:
  enabled: false
  extraConfig: |
    auto.create.topics.enable=false
    log.retention.hours=72
```

> `kubectl apply -f kafka-bitnami.yaml`：直接提交原生 K8s 资源清单（Service/StatefulSet/PVC 模板等），Kubernetes 原生 API 直接创建资源；无 helm 参与。

1. 编写 Kafka 配置 kafka-bitnami.yaml

```yaml
apiVersion: v1
kind: Service
metadata:
  name: kafka
  namespace: kafka
spec:
  selector:
    app: kafka # 选择所有 label【app=kafka】的Pod
  clusterIP: None # Headless 无VIP，支持pod独立域名
  ports:
    - port: 9092
      name: client
    - port: 9093
      name: controller
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
  namespace: kafka
spec:
  replicas: 3
  selector:
    matchLabels:
      app: kafka
  serviceName: kafka # 必须和service名称一致！生成稳定pod域名
  template:
    metadata:
      labels:
        app: kafka # Pod打上标签 app=kafka
    spec:
      containers:
        - name: kafka
          image: bitnami/kafka:3.9.0-debian-12-r4
          env:
            # brokerID直接使用pod hostname数字 kafka-0 → 0
            - name: KAFKA_BROKER_ID
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            # ========== KRaft 核心配置 ==========
            - name: KAFKA_CFG_PROCESS_ROLES
              value: "broker,controller"
            # 静态仲裁节点列表 headless完整域名
            - name: KAFKA_CFG_CONTROLLER_QUORUM_VOTERS
```

### 方式三：二进制自建 Kafka 镜像

> **自定义 Dockerfile**：自己编写 Dockerfile，可以基于【官方镜像 /bitnami 镜像 /alpine/debian 基础镜像】二次构建，完全自主掌控

#### 下载官方二进制包

地址：https://kafka.apache.org/downloads

下载：kafka_2.13-3.9.2.tgz

也可以用华为云镜像源，下载更快：https://mirrors.huaweicloud.com/apache/kafka/3.9.2/

#### 编写 Dockerfile

```dockerfile
# 使用Eclipse Temurin JDK21 Alpine（轻量LTS JRE）
FROM eclipse-temurin:21-jre-alpine

ENV TZ=Asia/Shanghai
ENV KAFKA_HOME=/opt/kafka
ENV PATH=${KAFKA_HOME}/bin:${PATH}

WORKDIR /opt

# 复制官方二进制压缩包到镜像内
COPY kafka_2.13-3.9.2.tgz /tmp/

# 解压、清理压缩包
RUN tar -zxf /tmp/kafka_2.13-3.9.2.tgz \
    && mv kafka_2.13-3.9.2 ${KAFKA_HOME} \
    && rm -f /tmp/kafka_2.13-3.9.2.tgz

# 暴露端口：业务9092、raft通信9093
EXPOSE 9092 9093

# 工作目录切换kafka根目录
WORKDIR ${KAFKA_HOME}

# 默认启动命令，后续k8s yaml覆盖command实现KRaft格式化与启动
CMD ["sh"]
```

## 总结：docker / kind / kubectl / helm 的关系层级

```text
你的Windows电脑
    ↓ docker（管理容器镜像、本地容器）
        ↓ kind（利用docker启动一整套K8s集群）
            ↓ kubernetes集群内部
                ├ kubectl：K8s集群的遥控器（操作集群资源pod/svc/ns）
                └ helm：K8s上的应用安装包管理器（基于kubectl和K8s API）
```


| 工具      | 定位                           | 类比                     | 管辖范围                |
|---------|------------------------------|------------------------|---------------------|
| docker  | 容器引擎，负责拉镜像、启停容器              | 汽车发动机                  | Windows 本机所有容器      | 
| kind    | 使用 docker 快速搭建一套完整 K8s 集群的工具 | 用发动机组装一整辆公交车 (K8s)     | 创建 / 删除整套 K8s 环境    |
| kubectl | K8s 集群官方客户端，K8s 遥控器          | 公交车上的控制面板，控制车内乘客 (Pod) | 某一套正在运行的 K8s 集群内部资源 |
| helm    | K8s 应用包管理工具，封装批量 yaml        | 一键套餐安装程序，底层调用 kubectl  | 向 K8s 集群批量部署应用      |

#### 1. docker：只管【容器、镜像】

✅ 工作范围：Windows 本机 Docker Desktop

**只认识容器、镜像、网络卷**；完全不懂 Pod、Namespace、K8s

常用命令：
```shell
docker pull xxx        # 拉镜像
docker images          # 查看本地镜像
docker ps              # 查看正在运行容器（kind集群本质就是一堆docker容器）
docker stop 容器id     # 停止容器
```
> 重点：kind 集群就是 docker 容器！你执行 kind create cluster，底层就是 docker 启动多个容器组成 K8s 控制面 + 节点。

#### 2. kind：用 docker 搭建「整套 K8s 环境」

kind = K8s 集群生成器

**只管两件大事：创建集群、销毁集群。**

```shell
kind create cluster    # 创建一套全新K8s集群（一堆docker容器诞生）
kind delete cluster    # 销毁整套K8s（所有节点容器全部删除）
kind get clusters      # 查看本机存在多少套独立K8s
kind load docker-image # 把Windows本地docker镜像导入kind集群内部（超级常用）
```

> ⚠️ kind 不管理 Pod、不管理 kafka！它只负责把 K8s 平台搭出来。
搭好平台之后，kind 任务完成，后续部署应用交给 kubectl/helm。

#### 3. kubectl：K8s 的原生遥控器（核心中枢）

只要你想操作K8s 集群里面的资源，全都靠它。

前提：必须通过 context 选定要连接哪一套 kind 集群。

操作对象：Node、Namespace、Pod、Service、PVC、ConfigMap……

```shell
kubectl config get-contexts   # 查看可以连接哪些K8s集群（读取本地文件，不连集群）
kubectl get nodes             # 查看当前K8s集群节点（kind创建出来的3个节点）
kubectl create ns kafka       # 在K8s集群内创建命名空间
kubectl get pods -n kafka     # 查询kafka命名空间下pod
kubectl port-forward          # 端口转发
kubectl delete pod xxx        # 删除Pod
```
> kubectl 本身不会创建容器！只是发指令给 K8s，由 K8s 调度容器。

####  4. helm：建立在 kubectl 之上的「应用安装工具」

helm 不能独立工作，依赖 kubectl 连通 K8s 集群。

原生 kubectl 部署中间件需要手写几十份 yaml。

helm 把一堆 yaml 打包成 Chart，一键部署整套应用（Kafka 集群）。

```shell
helm repo add       # 添加软件源
helm repo update    # 更新源缓存
helm install        # 部署应用到K8s集群（内部调用kubectl创建各类资源）
helm uninstall      # 卸载整套应用
helm upgrade        # 修改配置后更新集群
```

工作链路：
helm → 渲染 yaml 模板 → 调用 kubectl → 请求发送给 K8s → 创建 Pod/Service/PVC

#### 5. 完整流程串起来，直观看懂先后关系

```text
1. kind create cluster   【docker启动容器，组装出一套K8s集群】
2. kubectl 创建命名空间 【遥控器操作刚搭建好的K8s】
3. helm install kafka    【helm借助kubectl，向K8s申请创建ZK、Kafka所有资源】
4. K8s收到指令，通知docker拉取镜像，启动kafka容器
```

#### 6. 最容易混淆的几组对比（高频误区）

1. kind cluster VS namespace

    kind cluster：一整套独立 K8s 环境（大楼），由 kind 创建删除
    
    namespace：K8s 集群内部逻辑分区（大楼里房间），kubectl 操作

2. docker ps VS kubectl get pods

    docker ps：看到 Windows 层面原始容器（kind 节点、kafka 容器全部混在一起）
    
    kubectl get pods：从 K8s 视角查看应用，抽象了底层容器细节

3. helm 和 kubectl

    helm ≠ 替代品。

    helm = 批量生成 yaml 的工具；最终真正创建资源依旧靠 kubectl 和 K8s。
   
    > 如果不用 helm：需要手写大量 yaml，然后 kubectl apply -f xxx.yaml

#### 7. 极简记忆口诀

docker：管容器镜像（地基）

kind：用 docker 搭出 K8s 平台（整栋楼）

kubectl：操控 K8s 大楼内部一切资源（遥控器）

helm：一键装修套餐，借助遥控器批量布置房间（部署 kafka）

#### 8. 一个判断小技巧（以后分不清命令时自查）

命令开头 kind → 操作【整套 K8s 环境】

命令开头 docker → 操作【底层容器 / 镜像】

命令开头 kubectl → 操作【正在运行的 K8s 集群内资源】

命令开头 helm → 【在 K8s 里安装 / 升级应用】

### 执行命令：kubectl run

```shell
kubectl run kafka-debug --image=my-kafka:3.9.2-jdk21 --rm -it -- /bin/sh
```

临时创建 Pod 的即时命令，属于 kubectl run 临时调试用法。

逐条拆解含义：

- `kubectl run kafka-debug`

  在 K8s 集群临时创建一个 Pod，Pod 名字叫 kafka-debug

- `--image=my-kafka:3.9.2-jdk21`

  使用自建的 kafka 镜像启动

- `--rm`

  退出终端后，自动删除这个临时 Pod，不会残留资源（调试神器）

- `-it`

  交互式终端：i = 持续输入，t = 分配伪终端，相当于 docker run -it

- `-- /bin/sh`

  -- 表示：后面参数不再属于 kubectl，直接传给容器作为启动命令；

  作用：容器启动后直接运行 /bin/sh，进入交互式 shell
